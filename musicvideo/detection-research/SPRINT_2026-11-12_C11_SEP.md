## 1. What was built

A torch-free C11 runner for UVR-MDX-NET-Voc_FT (`wubuwizard-cpu-sep/UVR-MDX-NET-Voc_FT.onnx`,
SHA-256 `534b2070…ecce111`, 16.7M params, 178 nodes, 392 GMACs/chunk), in
`wubutv-network/musicvideo/detection-research/c11_sep/`:

- **STFT/ISTFT** (`sep_stft.c`, `sep_fft64.c`, `sep_fft.c`): reflect-pad, periodic Hann,
  complex-out, torch convention (raw DFT sums). FFT in **double** precision (mixed-radix
  2048×3 — n_fft=6144 is not a power of two); float32 2048×3 error was 1.67e-04 on this
  peaked spectrum, double puts the STFT at torch's own error. WuBuRVC's `wubu_stft.c`
  was NOT used (magnitude-only + zero-pad error); `wubu_fft.c`/`wubu_audioio.c` lego'd as-is.
- **Ops** (`sep_ops.c`): Conv 1x1/3x3 s1/2x2 s2, ConvTranspose 2x2 s2, MatMul, BN, Relu/Add/Mul,
  Transpose — all parity-checked against ORT layer outputs.
- **AVX512 SGEMM** (`sep_gemm.c`): 8×48 micro-kernel, 24 zmm accumulators, MC=128 NC=2048
  KC=256, OpenMP over M-tiles. 3x3 convs run as im2col-tiled GEMM (~118 GFLOPS), 1x1 convs
  as out^T GEMM (~63 GFLOPS), MatMuls direct. See `stage3a_gemm.json`.
- **Graph compiler** (`compile_graph.py`): 178 nodes → 173 instructions (5 ConvTranspose BNs
  folded; 22 post-MatMul BNs stay explicit — the weight is shared across channels while the
  BN scale varies per channel, so it cannot fold). 18 slots, arena 546 MB, weights 63.6 MB.
- **Interpreter** (`sep_interp.c`): slot-arena execution, per-instruction timing.
- **UVR driver** (`sep_main.c`): chunking/OLA per `mdx_onnx_cpu.py` (chunk 261120, step 195840,
  TRIM 3072, Hann OLA, peak-normalize, bins 0–2 zeroed, instrumental = mix − vocals×1.01).

### Stage 3b — full-graph interpreter parity: PASS (`stage3b_interp_parity.json`)
**24/24 checkpoints PASS** (16 original + 8 fine-grained nodes 46–58 added to localize
the first failure). Worst sample max|diff| 7.02e-04 (node 9, bar 1e-2); all others
≤4.8e-05. Node 177 (final output, FULL comparison): max|diff| **8.631e-05**, corr 1.000000.

Two real bugs found and fixed in this stage (both are now regression notes, see §4):
1. **Slot-shape aliasing** — ops read tensor shapes from the static `slots[]` table, but
   slots are reused across different shapes with the same numel (slot 6 first held
   [96,128,192] but BN 58 is [192,32,384]). First symptom: node 58 BN failed
   (max|diff| 6.44, corr 0.74) while node 57 MatMul passed. Fix: every op now takes its
   shape from the **instruction dims**, never from `slots[]` (only arena offsets come
   from the slot table). A first attempt that updated the slot shape on reuse made it
   worse (swapped slots 1/2, broke every Transpose downstream of node 2) and was reverted.
2. **Checkpoint array overflow** — `test_interp.c` held `ckpts[16]` but `checkpoints.json`
   now has 24 entries; the parser wrote past the array and silently dropped node 75
   (INTERP: FAIL with all visible lines PASS). Fix: array is now `ckpts[32]`.

## 3. The twiddle-table race (found in Stage 3c, fixed)

The first smoke run produced a **correct R channel and a garbage L channel**
(L corr −0.0009, RMS 5891 vs ORT 9.4, clipping at ±32767; R corr 0.99998).
Root cause: `build_tw_tables()` (`sep_fft.c`) and `build_tw64()` (`sep_fft64.c`) build
their static twiddle tables **lazily on first FFT call, with no synchronization** —
and the STFT/ISTFT call the FFT from inside OpenMP parallel regions. The first
parallel call raced the build: the L-channel STFT's frame 8 (first frame of the
second thread's chunk under `schedule(dynamic, 8)`) read a half-filled table
(max err 2.2e-02 vs 1.5e-05 elsewhere); the ISTFT race corrupted the L vocals outright.
Fix: `sep_fft_init()` / `sep_fft64_init()` build the tables eagerly, called from
`sep_stft_create()` (single-threaded, before any parallel region); the lazy builders
are now also guarded by an OpenMP critical section (double-checked). Re-verified:
all 4 input channels match ORT to ~1.5e-05, Stage 1 parity still PASS, smoke L/R both
1 LSB. **Lesson: lazy singletons + OpenMP parallel regions = a race; build tables
eagerly in the (single-threaded) constructor.**

## 4. Regression notes (do not reintroduce)

- Ops must read shapes from **instruction dims**, never from the slot table
  (`sep_interp.c`: OP_BN, OP_TRANSPOSE_HW, OP_RELU, OP_ADD, OP_MUL all use `in->d0..d2`).
- `test_interp.c` checkpoint array must exceed the checkpoint count in
  `checkpoints.json` (now 32 slots for 24 checkpoints).
- FFT twiddle tables are built **eagerly** in `sep_stft_create()`; never call the FFT
  from a parallel region before a `sep_stft_create()` has run in the process.
- `compile_graph.py` does NOT update `slots[]` shapes on reuse (a static table cannot
  represent a slot holding different shapes at different times).

The blade is a shared VM (1.5 CPUs) and was under heavy competing load for much of

  GFLOPS) and the 1x1 convs (out^T GEMM at ~63 GFLOPS) — the next speed lever
  is the wubuwizard int8 quantized-matmul path (scoped, not built here).

## 7. Reboot resilience (how Stage 4 actually got done)

Two single-process full runs were SIGTERM'd by VM reboots (the first at ~70 min
in, the second at ~7 min in; the blade reboots roughly every ~2 h — `uptime`
showed 2 min after the second kill). The fix is a **resilient dump mode** in
`sep_main.c` (`--dump-dir`): each chunk's raw ISTFT output is written to
`<dir>/chunk_%03d.bin` ([start, actual] int32 header + L/R floats) as soon as
it is computed, and chunks whose dump already exists are skipped on re-run — so
a reboot loses at most the in-flight chunk. `assemble_chunks.py` then does the
Hann OLA + divide + trim + rescale from the dumps (replicating
`mdx_onnx_cpu.py`'s demix exactly). The 37 chunks were produced in 4 batches
+ chunk 0, then assembled; a separate clean single run (840.4 s) confirmed the
timing bar and agreed with the batched output to ≤1 LSB. **Lesson: on this
blade, any job longer than ~1 h must checkpoint per unit of work — a single
long process will not survive the reboot cadence.**
Deleted to relieve the disk quota: `ref_chunk0.npz` (56.6 MB — fully redundant)
and `chunk_dumps_clean/` (77 MB — the clean timing run's dumps; the timing is
recorded in `clean_run.log` and the output agreed with the batched dumps to
≤1 LSB, so the dumps themselves are redundant).
